# QA：Night Shift 与投资日报的关系（架构师结论）

> 范围：只回答 Jimmy 的两个问题，不改业务代码。
> 依据：题面给出的边界。本仓库不含二者实现，结论基于边界推断，未做代码级验证。
> 日期：2026-09-20

## 0. 输入边界

- 持仓核心：crypto（24/7 市场）。
- Night Shift：隔夜 X ingest → ~07:00 研报。看社区动态 / 叙事。
- 投资日报：~08:29，持仓优先再定价。输入 = AI 融资/并购/IPO/行情 + BTC/宏观。
- ROLE_MAP：二者不互相顶班。

## 1. 结论

### Q1 无社区动态时，投资日报结论是否可靠？——有条件可靠

日报对"它所测量的东西"（宏观、行情、deal flow、BTC 价格）是可靠的，因为它设计上不依赖 X 数据。
但对 crypto 持仓，它缺的是**领先指标**：叙事拐点、exploit / depeg / 交易所异常 / 监管传闻。这些通常先出现在 X、后反映到价格。

- 日报可靠 = "基于宏观与价格的再定价可靠"
- 日报不可靠 = "把它当成 crypto 持仓的完整风险画面"

关键：必须区分两种"无社区动态"。

| 情形 | 含义 | 日报应如何处理 |
|---|---|---|
| A. Night Shift 正常跑完，确实无信号 | "安静的夜"，本身是信息 | 结论可靠，注明"隔夜社区无异常" |
| B. Night Shift 没跑 / ingest 失败 / X 限流 / 0 条 | 未知，不等于安静 | 结论标"降级"，crypto 结论降置信度，不出加仓类建议 |

当前唯一的架构缺口：如果日报分不清 A / B，它会把"缺失"当成"平静"。修法见 §4。

### Q2 是否合并？——不合并

- 回答的问题不同：Night Shift 答"社区在说什么 / 叙事变没变"（信息）；日报答"我的持仓怎么重定价"（行动）。
- 失败模式不同：X ingest 依赖外部 API（限流、鉴权失败常见），是长时间流式任务；日报是定时批处理，输入为结构化行情数据。合并 = 把核心产品日报的 SLA 绑到 X API 可用性上。
- ROLE_MAP 已规定不互相顶班，合并等于推翻这条约束。
- 可逆性：分离 + 薄接口可逆；合并后 prompt / 模板 / 调度耦合，拆回来成本高。

不合并的代价：Jimmy 读两份；BTC 价格等少量信息重复。可接受，用 §4 握手文件缓解。

**推翻条件（何时重新考虑合并）**
- 一段时间内，日报的 crypto 结论过半被 Night Shift 的信息修正；
- Jimmy 长期只读其中一份；
- 两套调度的运维成本明显超过独立价值。

## 2. 可靠边界

| 维度 | 日报可靠 | 日报不可靠 / 需借助 Night Shift |
|---|---|---|
| 宏观（利率、CPI、美元、流动性） | ✅ | — |
| BTC / 主流币价格与已发生的波动 | ✅（价格是滞后汇总，社区驱动的行情已部分体现） | 解释"为什么动"、判断"会不会继续" |
| AI 融资 / 并购 / IPO | ✅ | — |
| 叙事拐点、meme / 空投 / 板块轮动 | ❌ | Night Shift |
| exploit / depeg / 交易所异常 / 监管传闻 | ❌（价格反映前有窗口） | Night Shift |
| 07:00 → 08:29 窗口内的社区事件 | ❌ | 日报自行取 BTC 价格 + 资金费率 / 爆仓数据兜底 |
| Night Shift 状态未知时 | ⚠️ 只能给降级结论 | 必须显式标注 |

一句话：**日报对"已发生的、可量化的"可靠；对"正在发酵的、叙事性的"不可靠，且不应假装可靠。**

## 3. 产品边界表

| | Night Shift | 投资日报 |
|---|---|---|
| 时间 | 隔夜持续 ingest → ~07:00 研报 | ~08:29 定时批 |
| 输入 | X（社区 / KOL / 项目方） | AI 融资/并购/IPO、行情、BTC、宏观 |
| 输出 | 研报：社区动态、叙事变化、异常信号 | 持仓再定价：每个持仓的观点 / 动作建议 |
| 回答的问题 | "发生了什么、大家在说什么" | "我该怎么看我的仓位" |
| 决策类型 | 信息 / 预警 | 行动 |
| 主要失败模式 | X API 限流、鉴权、0 覆盖 | 行情源缺失、宏观日历错位 |
| 失败时 | 输出"失败 / 部分覆盖"状态；不补跑到 08:29 | 照常出报但标注降级；不代跑 X ingest |
| 依赖方向 | 不读日报 | 只读 Night Shift 握手文件（§4），不读原始 X 数据 |
| 共享 | 持仓清单（单一来源）、资产别名表 | 同左 |
| 不共享 | prompt、模板、调度器、数据源 | 同左 |
| ROLE_MAP | 不顶班日报 | 不顶班 Night Shift |

## 4. 不合并时的最小耦合

原则：**单向、只传状态与摘要、不阻塞。**

1. **单向依赖**：日报 → 读 Night Shift；Night Shift 永不读日报（避免环）。
2. **握手文件**（唯一接口）：Night Shift 在 ~07:00 研报生成后写出，例如 `nightshift/handoff/YYYY-MM-DD.json`。

   ```json
   {
     "date": "2026-09-20",
     "status": "ok | empty | partial | failed",
     "ingest_window": { "start": "...", "end": "..." },
     "post_count": 0,
     "coverage": { "expected_sources": 0, "covered_sources": 0 },
     "top_signals": [
       { "asset": "BTC", "direction": "bearish|bullish|neutral", "confidence": 0.0, "source_count": 0, "summary": "..." }
     ],
     "holdings_flags": [
       { "asset": "ETH", "level": "none|watch|alert", "reason": "..." }
     ],
     "report_path": "nightshift/reports/2026-09-20.md",
     "generated_at": "..."
   }
   ```

   `top_signals` ≤ 5；`holdings_flags` 只覆盖持仓清单中的资产。日报只消费此文件，不碰原始 X 数据。
3. **日报侧契约**
   - 每份日报固定一行："隔夜社区覆盖：{status} / {post_count} 条 / 覆盖 {covered}/{expected}"。
   - `status != ok` → crypto 相关结论标"降级"，不输出加仓 / 加杠杆类建议（或置信度上限下调一档）。
   - `holdings_flags` 中有 `alert` → 对应持仓段落必须引用并回应，不能沉默。
4. **时序**：握手文件 deadline 07:30；08:00 仍缺 → 日报按 `status=missing` 处理，**不等待、不重试 ingest**（重试 = 顶班，违反 ROLE_MAP），只发一条告警。
5. **共享的单一来源**：持仓清单、资产别名表（ticker 归一化）两者读同一份，保证两份报告说的是同一批资产。除此之外不共享。
6. **不做的事**：不做共享 prompt 库、不做统一调度框架、不做"日报失败时 Night Shift 补出简版日报"。这些都是合并的变体。

## 5. 置信度

| 结论 | 置信度 | 依据 / 会降低置信度的情况 |
|---|---|---|
| Q1：有条件可靠，需区分"安静"与"缺失" | 高（~0.8） | 基于题面边界推断日报不依赖 X 输入；若实际 prompt 隐式读取了 Night Shift 研报，则 Night Shift 失败时日报可靠性低于此结论 |
| Q2：不合并 | 中高（~0.75） | 主要依据是失败模式隔离与 ROLE_MAP 约束；若 §1 推翻条件出现，应重新评估 |
| §4 最小耦合方案 | 中（~0.7） | 字段为建议值，需按实际持仓清单与研报格式校准；本 QA 未读到二者实现代码 |
